# Build Plan — v0.1.4 "Connect"

**Status:** implemented (2026-10-23). **Version:** 0.1.3 → **0.1.4**.
**Theme:** attach to a real Firefox and hold one BiDi session. No browsing tools
beyond status yet.

This is the first release that talks to Firefox. It is still local-only; the
first public npm release stays **v0.2.0**.

## 1. Goal

A user starts Firefox with `--remote-debugging-port`, rebuilds, restarts the MCP
server, and gets:

- `ping.status` — `connected: true` with browser version and profile.
- `browser.status` — session state, browser version, profile, context count.
- `browser.profiles` — discovered Firefox profiles and which one is live.
- `browser.connect` / `browser.disconnect` — explicit session control.
- A clear `BIDI_SESSION_BUSY` error when another BiDi client owns the session.

No snapshot, no tabs, no navigation, no input, no network, no devtools.

`src/tools/ping.ts` is updated to read the session state instead of returning
`connected: false` unconditionally.

### 2.2 `bidi-client.ts`

- Connect to a `ws://`/`wss://` URL with a timeout.
- Monotonic request IDs; `Map<id, {resolve, reject, timer}>`.
- Resolve on `{type:"success"}`, reject on `{type:"error"}` with an
  `ActionableError`.
- Dispatch `{type:"event"}` to the event pipeline without blocking commands.
- On close: reject all pending requests, mark state `disconnected`, emit one
  close event. **No automatic reconnect loop.**
- No `session.new` here; that is the session manager's job.

### 2.3 `browser-discovery.ts`

Auto-detection is required. No env var is needed in the common case.

Resolution order:

1. `BIDI_WS_URL` — optional override only.
2. `BIDI_PROFILE_DIR` + `<profile>/WebDriverBiDiServer.json`.
3. Firefox/Zen `profiles.ini` roots, then discovery files.
4. Running process command lines (`--remote-debugging-port=...`).
5. Loopback ports `9222` and `9223` as the last fallback.

Rules:

- `WebDriverBiDiServer.json` is `{ ws_host, ws_port }`; build
  `ws://host:port/session`.
- Never trust the file alone: probe the endpoint.
- Running-process discovery is read-only; we never relaunch or mutate the browser.
- Non-loopback hosts require `BIDI_ALLOW_REMOTE=1`.
- Every failure returns `DISCOVERY_FAILED` with the exact Firefox start command.
- `pnpm setup` and `pnpm smoke` must work without any env var.

#### Process discovery details

Firefox and Zen do not expose an in-browser toggle for the Remote Agent. The only
supported way is still `--remote-debugging-port`. So v0.1.4 adds a small,
platform-specific process scan as a fallback:

| Platform | Source | Notes |
|---|---|---|
| Windows | process command lines for `firefox.exe`, `zen.exe`, `librewolf.exe`, `waterfox.exe`, `floorp.exe` | Prefer command-line discovery over blind port probing |
| macOS / Linux | process command lines for the same binaries | Use `ps`-style command lines; no daemon, no root |
| Any | pure helper `extractRemoteDebuggingPort(commandLine)` | Unit-testable without spawning a browser |

Rules:

- Never mutate the user's browser profile or relaunch Firefox from the server.
- Never expose the process command line itself; only the parsed port and endpoint.
- Treat multiple candidates as candidates, not as a single source of truth. The
  final URL is verified with `session.status`.
- If a process is found but the port is unreachable, discard that candidate.

#### `browser.profiles` shape

`browser.profiles` becomes the main discovery surface:

```json
{
  "ok": true,
  "action": "profiles",
  "data": {
    "candidates": [
      {
        "endpoint": "ws://127.0.0.1:9223/session",
        "source": "process-cmdline",
        "profilePath": "C:/Users/.../Profiles/abc.default",
        "processId": 1234,
        "live": true
      },
      {
        "endpoint": "ws://127.0.0.1:9222/session",
        "source": "profile-file",
        "profilePath": "C:/Users/.../Profiles/xyz.default",
        "live": false
      }
    ]
  }
}
```

`live` is only true after a successful `session.status` probe. `processId` is
diagnostic only and never used to kill a browser.

### 2.4 `session-manager.ts`

- Idempotent `connect()`: one in-flight promise; one `session.new`.
- On `session.new` with "Maximum number active sessions" → `BIDI_SESSION_BUSY`
  with port/profile and a fix. **Never retry.**
- `disconnect()` calls `session.end`; never `browser.close`.
- `status()` returns `{ connected, sessionId?, browser?, profile?, contexts? }`.
- On WebSocket close: invalidate session state, keep discovery info.
- Owns the one session for the whole server process.

### 2.5 `event-pipeline.ts`

- Subscribe once after `session.new` to `browsingContext.*` and `log.*`.
- Typed handler map; no tool consumes events yet.
- Bounded buffers are set up here but not exposed until v0.1.5.

### 2.6 `browser` tool

| Action | Risk | Returns |
|---|---|---|
| `status` | read-only | connected, session ID, browser version, profile, context count |
| `profiles` | read-only | discovered endpoints + `source: profile-file \| process-cmdline \| port-probe`, live marker |
| `version` | read-only | server + Firefox versions |
| `connect` | idempotent | session result or `BIDI_SESSION_BUSY` |
| `disconnect` | destructive to session only | ends session; Firefox stays open |

`browser.close` is **not** in this release. It stays gated for later.

### 2.7 Config additions

| Variable | Default | Purpose |
|---|---|---|
| `BIDI_ALLOW_REMOTE` | `false` | Permit non-loopback `BIDI_WS_URL` |
| `BIDI_DISCOVERY_ROOTS` | empty | Extra profile roots, `;`-separated |
| `BIDI_SESSION_TTL` | `0` (off) | Future idle TTL; validate now, enforce later |

Existing `BIDI_HOST`, `BIDI_PORT`, `BIDI_WS_URL`, `BIDI_PROFILE_DIR`,
`BIDI_TIMEOUT`, `BIDI_TOOLSET` are reused.

### 2.8 MockBiDiServer extensions

- `session.status` with configurable `ready`.
- `session.new` success, and a `failSessionNew()` mode that emits the "Maximum
  number active sessions" error.
- `session.end`.
- Configurable response delay for timeout tests.
- `drop()` to close the socket.
- Fixture registry already present stays.

### 2.9 Dev scripts and setup folder

`pnpm setup` and `pnpm smoke` are the zero-config dev loop. They are not shipped
to npm and never contain machine-specific paths.

| Script | Purpose |
|---|---|
| `scripts/setup.mjs` | install → build → test → verify → smoke probe |
| `scripts/dev-smoke.mjs` | zero-config Firefox/Zen probe using the real discovery module |
| `scripts/dev-detect.mjs` | show Firefox-family processes and the parsed Remote Agent port |
| `setup/README.md` | optional platform-specific helpers; never ships to npm |

## 5. Out of scope

- Tabs, navigation, snapshot, input, forms, network, storage, emulation,
  extensions, devtools.
- Browser launch, private/incognito, broker, cross-browser.
- `browser.close`.
- npm publish.

## 6. Risks

- **Discovery is the top risk.** Profile roots differ on Windows/macOS/Linux and
  portable installs. Mitigate with `BIDI_WS_URL`/`BIDI_PROFILE_DIR`, `profiles.ini`
  parsing, and a dead-port probe. See `risk-register.md` R4/R5/R27.
- **Remote Agent prefs.** Firefox applies recommended prefs on the default
  branch for the session. Our server writes nothing; document
  `remote.prefs.recommended=false`. See R26/R31.
- **`navigator.webdriver` stays true.** No config can change it; document only.
- **BiDi version drift.** Feature-detect `session.new` capabilities; never assume
  a module exists.

## 7. Release policy

Keep v0.1.4 local. Tag it only as an internal milestone. The first public npm
release remains v0.2.0, after snapshot and observe land.

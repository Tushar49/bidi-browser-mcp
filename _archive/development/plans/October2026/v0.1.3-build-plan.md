# Build Plan — v0.1.3 "Carcass"

**Status:** implemented (2026-10-21). **Version:** 0.1.0 → **0.1.3**.
**Theme:** a small, organized, tested skeleton that later waves fill in.

This release is intentionally boring. It creates the project shape, contracts,
reusable utilities, tool registry, a mock BiDi server, and one `ping` tool. It
does **not** connect to Firefox or expose browsing tools.

## 1. Why 0.1.3

- 0.1.0 is the current bootable stdio scaffold.
- 0.1.1/0.1.2 are reserved for the packaging/promote fixes already landed.
- 0.1.3 is the first **structured** codebase: directories, contracts, tests,
  and contributor rules.
- 0.2.0 is the first useful browser release (connect + snapshot + observe).

## 2. Locked decisions (minimal recommended options)

| Decision | Value |
|---|---|
| Default toolset | `core` |
| First browser release | v0.2.0 |
| Minimum Firefox | Core 129+; recommended 153 ESR; full surface 158+ |
| Debugger/profiler | v0.5, opt-in `devtools` |
| Extension install | opt-in + path allowlist |
| `browser.close` | opt-in only |
| Browser launch | out of scope for v1 |
| Cross-browser | backend seam now; Chromium later; Safari deferred |
| Snapshot | DOM traversal + `sharedId`; no AX tree |
| Session | one per server process; broker future |

### 3.2 `config.ts`

- One env reader; no `process.env` anywhere else.
- Defaults:
  - `BIDI_HOST=127.0.0.1`
  - `BIDI_PORT=9222`
  - `BIDI_WS_URL` unset
  - `BIDI_PROFILE_DIR` unset
  - `BIDI_TIMEOUT=30000`
  - `BIDI_TOOLSET=core`
  - `BIDI_OUTPUT_MODE=full`
  - `BIDI_MAX_INLINE_LEN=60000`
  - `BIDI_TEMP_DIR=.temp`
- Validation: positive integers, enum values, loopback URL by default.
- Export a frozen `Config` object and a `loadConfig(env = process.env)` for tests.

### 3.3 `types.ts`

- `ToolAction`, `ToolDefinition`, `ToolHandler`, `ToolResult`.
- `ServerContext` (config + version + logger; no connection yet).
- `StructuredResult<T>` with `{ ok, action, data?, error?, warnings? }`.
- `ActionableErrorCode` union.
- BiDi envelope types (`BiDiCommand`, `BiDiResponse`, `BiDiEvent`) for the mock
  server and future client.
- No `any` without a comment.

### 3.4 `utils/errors.ts`

- `ActionableError` with `code`, `fix`, `details`.
- `toActionableError(unknown)`.
- Codes for the full roadmap (discovery/session/context/UID/action/network/
  extension/unsupported), even if unused yet.
- `formatError()` for MCP text output.

### 3.5 `utils/result.ts`

- `ok(action, data, warnings?)`.
- `fail(action, error)`.
- `toToolResult(result)`:
  - `structuredContent` always;
  - serialized JSON text block;
  - `isError: true` on failure;
  - no base64, no huge payloads.
- File overflow is a later addition; v0.1.3 only enforces a max length.

### 3.6 `utils/assert.ts`

- Tiny guards: `assertString`, `assertBoolean`, `assertEnum`, `assertPositiveInt`.
- Throw `ActionableError` with `INVALID_ARGUMENT`.
- No schema library; keep runtime deps at two.

### 3.7 `tools/base-tool.ts`

- `defineTool({ name, title, description, actions, annotations, handler })`.
- `action` is a string enum per tool.
- `COMMON_PARAMS` (for later: `context`, `timeout`).
- `validateAction(tool, action)`.
- No zod; tools validate their own args with `assert.ts` (or a future tiny
  schema helper).
- Annotations are passed to `registerTool`.

### 3.8 `tools/registry.ts`

- Register tools by name; reject duplicates.
- `listTools()` returns SDK tool definitions.
- `dispatch(name, args)` routes to the handler.
- `filterByToolset()` for `BIDI_TOOLSET`.
- Unknown tool/action returns `TOOL_NOT_FOUND` / `INVALID_ACTION`.
- No global singleton; registry instance is created per server.

### 3.9 `tools/ping.ts`

| Action | Returns |
|---|---|
| `status` | `{ serverVersion, connected: false, browser: null, uptimeMs }` |

Read-only, no browser dependency. Proves the tool contract end to end.

### 3.10 `index.ts`

- Create `ServerContext` from config.
- Create registry; register `ping`.
- `ListTools` returns registry tools.
- `CallTool` dispatches and converts to MCP result.
- No side effects on import.
- `createServer()` keeps accepting no transport.

### 3.11 `__tests__/mocks/bidi-server.ts`

- `ws` server on port `0` (ephemeral).
- Routes:
  - `session.status` → `{ ready: true, message: "" }`
  - `session.new` → session ID + capabilities
  - `browsingContext.getTree` → fixture tree
  - `script.evaluate` → fixture result
  - unknown method → BiDi error
- `sendEvent(method, params)`.
- `requests` array for assertions.
- `start()`/`stop()`/`url`.
- No real browser; closes cleanly in `afterEach`.

## 4. OpenCode local vs published config

The active config lives outside the repo at:

```text
<config-dir>/opencode/opencode.jsonc
```

It currently has a staged V2 shape (`mcp.servers`). Add a `bidi-browser` entry.

### Dev (this branch, local path)

```jsonc
"bidi-browser": {
  "type": "local",
  "command": [
    "node",
    "<repo>/dist/bin.js"
  ]
}
```

- Run `pnpm build` after changes.
- Restart the MCP server in OpenCode (`/mcps`) so it reconnects to the new build.
- The absolute path is machine-specific and lives only in local config, never
  in repo files.

### Published (npm)

Recommended for clients:

```jsonc
"bidi-browser": {
  "type": "local",
  "command": ["pnpm", "dlx", "bidi-browser-mcp@latest"]
}
```

Fallback:

```jsonc
"command": ["npx", "-y", "bidi-browser-mcp@latest"]
```

Global install (optional):

```bash
pnpm add -g bidi-browser-mcp
# then:
"command": ["bidi-browser-mcp"]
```

Global install is fine for a single user who wants the binary on PATH, but
`pnpm dlx ...@latest` is better for MCP clients because it pins less and avoids
stale global versions. Do not put the dev path in the published README.

## 5. Release policy for 0.1.3

A package with only `ping` is not useful to npm users. Two options:

- **Recommended:** tag `v0.1.3` as a local milestone only; do not publish npm.
  Use it to validate the carcass and the local MCP wiring. First public npm
  release is **v0.2.0**.
- **Pipeline validation only:** publish `0.1.3-dev.0` as a prerelease
  (`alpha` dist-tag), never `latest`. This proves OIDC/packaging without
  advertising a no-tool server.

Do not publish stable `0.1.3` as `latest`.
